# Keep the game alive without diluting it

Longevity is a design and maintenance goal, not a guarantee. Randomly rotating the same trap forever is not enough. Use replayable foundations now and add meaningfully different interactions over time.

## Shipped in this alpha

Campaign progression; three-star shard goals; local efficiency scores; visual cosmetics earned through completion; deterministic UTC dailies; reproducible challenge families; fast retries without energy or revival purchases; modular content and tests; offline-first packaging.

## Next acceptance milestone: one polished world

Replace the first six modular routes with hand-authored layouts from the design: a receding exit, actual key routing, timed fading bridges, and a distinctive world-ending test. Retain the working light/jump mechanics. Observe first-time players on a real Android phone. Validate that each new trap teaches a readable rule before combining it with another.

## New content, not artificial chores

Add a small new mechanic together with a few curated levels. Keep earlier chapters playable. Add optional mastery medals only when they measure a real skill. Avoid daily streak penalties, mandatory logins, endless stat inflation, or rewards that make hard levels easier for paying players.

Future candidates: interactive echo recordings, gravity inversion with ceiling support, moving lifts, shadow train, a multi-part final encounter, a local level editor with validated challenge seeds. None of these are represented as already implemented.

## Production milestones

1. Physical-device input, readability, frame-time, thermal and battery review.
2. Curated first-world difficulty and visual polish; improve warnings rather than adding checkpoints.
3. Android packaging with signed release builds, lifecycle testing, privacy documentation, and store review.
4. Only after gameplay testing: optional cosmetic monetization outside runs. No revival or power purchases.
5. If competition becomes important: backend validation, anti-tamper strategy, accounts only if needed, and an explicit privacy/consent design. Local scores are not trusted server scores.

## Measure before deciding

With player consent and an appropriate data policy, examine voluntary return rate, completion by stage/variant, repeated death locations, input mistakes, and frame-time problems. The current build sends no analytics. Do not invent retention targets or revenue forecasts. Feedback and maintenance capacity should set the release cadence; no future update schedule is promised by this repository.
